CymBuild Server Deploy Guide

How to deploy the CymBuild API and PWA, and migrate the database, to QA or UAT on SOC-CONIIS with one PowerShell command.

Written 13 Oct 2026Branch feature/SB_ServerDeploy-26.4-qa-publishUp to commit f3bea4de

Overview

CymBuild is not deployed through a pipeline. This script replaces the old manual process of publishing to a folder, backing up by hand and copying files over RDP. It builds once from your clean checkout, copies a hash-verified package to the server, migrates the database, switches the live folders, checks they answer, and rolls back automatically if they don't.

Each environment keeps its files under its own deploy root on the server: C:\CymBuildDeploy\QA or C:\CymBuildDeploy\UAT.

Before you start

  • PowerShell 7.2+ and the .NET 10 SDK on your machine.
  • An admin account on SOC-CONIIS, such as ESGL\stephen.brett_adm or ESGL\Oliver.Eros_adm. Open PowerShell as that account and the script uses your login without prompting. Otherwise it prompts for <you>_adm.
  • A clean, committed working tree. The script refuses to build anything that isn't committed. Deploy from a release/* branch where you can; any other branch gets a warning.
  • SQL rights for your _adm account on the target database: BACKUP DATABASE, DDL, and read and write on the SMigration tables. You also need CREATE DATABASE on the target instance, because the backup check (RESTORE VERIFYONLY) requires it.
  • Nobody using a schema workbench on the source or target database while the database phase runs.

UAT permission still pending

On the SQL instance named in appsettings.Test.json, your _adm account can back up the UAT database but not verify the backup. Until the DBA runs GRANT CREATE DATABASE in master on that instance for the deploy accounts, UAT deploys the application but skips schema and metadata.

Commands

Run these from the repository root. Always preview with -WhatIf first. It runs the local checks and the read-only server checks, prints the plan and both databases, and changes nothing.

./tools/Deployment/Publish-CymBuildServer.ps1 -Environment UAT -WhatIf

./tools/Deployment/Publish-CymBuildServer.ps1
Deploy to UAT (database migrated from QA)
./tools/Deployment/Publish-CymBuildServer.ps1 -Environment UAT
Deploy one component only
./tools/Deployment/Publish-CymBuildServer.ps1 -Component Api
./tools/Deployment/Publish-CymBuildServer.ps1 -Component Pwa
Application only, no database phase
./tools/Deployment/Publish-CymBuildServer.ps1 -SkipDatabase

./tools/Deployment/Publish-CymBuildServer.ps1 -RestoreBackup latest

ParameterMeaning
-EnvironmentQA (default) or UAT.
-ComponentApi, Pwa or both (default).
-SkipDatabaseDeploy the application without backup, schema or metadata.
-WhatIfChecks and plan only. Nothing is built, backed up, migrated or copied.
-RestoreBackuplatest or a backup folder name. The current files are backed up first, so a restore can itself be undone.

A real deploy asks for confirmation once. It asks again only if the new build would remove files from the server, other than Blazor's renamed _framework files.

Where database names come from

Database names change between releases, so the script never hard-codes them. It reads the server and database from the committed services/Concursus.API/appsettings.<Env>.json in the commit you're deploying. It checks the connection strings in the same order the API does: DefaultConnection, then ShoreDB, then CymBuild.

Deploying toTarget database read fromSource database read from
QAappsettings.QA.jsonappsettings.Development.json (DEV)
UATappsettings.Test.jsonappsettings.QA.json (QA)

Server and database are never written into the script, this guide or the deploy docs. To see which databases a deploy will use right now, run -WhatIf. Both are printed before the confirmation prompt, along with the file and key each came from:

Example -WhatIf lines
    Target DB : <server> / <database>  (appsettings.Test.json ConnectionStrings:ShoreDB)
    Source DB : <server> / <database>  (QA, appsettings.QA.json ConnectionStrings:ShoreDB)

When a database is renamed, update that file so it matches the server's own appsettings, commit it, then deploy.

The script stops before doing anything if:

  • the file has no connection string, or the string has no Data Source or Initial Catalog;
  • the target looks like LIVE: a database called Concursus, or a name or server containing live, prod or production;
  • the source and target are the same database.

The base appsettings.json is never used as a fallback. Only the named per-environment file counts.

What a deploy does

  1. Local checksThe working tree must be clean. The script records the branch and commit and resolves both databases.
  2. Server preflight (read-only)Connects to SOC-CONIIS over WinRM and checks that the service, IIS site and app pool exist and point at the expected folders. It also checks that the server-owned config files are present, at least 10 GB is free, and no other deploy holds the lock.
  3. BuildRuns dotnet publish -c Release for each component, writes a SHA-256 manifest of every file, and zips the lot under artifacts/server-deploy/<release>/.
  4. Transfer and stageCopies the zip to the server, checks its hash, extracts it to <deploy root>\releases\<release> and re-verifies every file. Lists config keys the build expects but the server lacks, by name only, and any server files the build would remove.
  5. Database phaseBackup, then schema, then metadata. See Database phase. A failure here is reported but never stops the application deploy.
  6. SwitchBacks up the live folders to <deploy root>\backups\before-<release>. For the API: stop the service, mirror the files, verify hashes, start it, wait 30 s, and check the URL answers. For the PWA: stop the pool, mirror, verify, start, and check the home page and appsettings.json.
  7. Roll back on failureIf anything fails after a live folder changed, that component is restored from the backup taken in the previous step and restarted.
  8. RecordAppends to history.log, writes current.json, and prunes releases and backups beyond -KeepReleases.

Files the server owns

These are never copied from the build, overwritten or deleted: appsettings*.json in any folder, web.config, nlog.config and the logs\ folder. When a build needs a new config key, the deploy warns with the key name. Add it to the server's appsettings.json yourself.

Database phase

Back up target→Schema→Metadata→Switch the application

The rules

  • A verified backup comes first. The script takes a COPY_ONLY, CHECKSUM backup to the target instance's default backup folder, named <database>_<release>.bak, then runs RESTORE VERIFYONLY. If either fails, schema and metadata are skipped.
  • Schema runs next. If it fails, metadata is skipped.
  • Metadata runs only after schema succeeds, or after schema finds nothing to do.
  • Database failures never stop the application deploy. They appear in the summary, and you complete schema and metadata yourself through the workbenches.

How runs are chosen

For both schema and metadata, an accepted run that hasn't been applied takes priority. If there isn't one, the script creates a new run with every Different and Missing in Target item selected.

  • Schema. Objects that would fail validation are skipped and listed with the reason. The selected definitions are synced from the source into Database\CymBuild_DB\Schema and committed to your current branch, not pushed, because the runner only applies committed files. The runner then applies the run, refusing any run compared more than 30 minutes earlier.
  • Metadata. Only Insert and Update rows in tables with an apply handler are selected, plus their dependencies. Retirements are never selected. Rows in tables without a handler are listed but not selected.

Push the schema commit

If the summary says a schema sync commit was created, review it and push it with the release. For UAT the source is QA, which was deployed from committed files, so normally no files change.

Protection against overlapping runs

Since commit f3bea4de, the bootstrap only re-creates a lifecycle procedure if its definition has actually changed. While SCore.PreDeploymentScript or SCore.PostDeploymentScript is running, the bootstrap also waits on the CymBuild.SchemaLifecycle lock instead of replacing the procedure mid-run. The QA and UAT APIs get this protection only once they're redeployed from that commit or later.

Reading the output

The run ends with a database summary, then a final line. Each step is Succeeded, Failed or Skipped, with the log path.

    Metadata  Skipped   Skipped: no verified backup.

Rolling back

Application. Run -RestoreBackup latest for the environment, or name a specific backup folder. The current files are backed up before the restore.

Database. Restore the .bak file the deploy took, from the target instance's default backup folder. The file is named <database>_<release>.bak and its full path is printed in the deploy output. Database restores are done by hand, never by the script.

Troubleshooting

"Working tree has uncommitted changes"
Commit or stash your changes. A deploy has to map to one commit. -WhatIf still runs, with a warning.
"Remote preflight failed; nothing was changed"
The lines marked BLOCKED say why: a service or site pointing somewhere unexpected, low disk space, or a deploy lock. Delete deploy.lock in the deploy root only if you're sure no other deploy is running.
Backup failed: "CREATE DATABASE permission denied"
The backup was written, but RESTORE VERIFYONLY needs CREATE DATABASE permission, which your account lacks on that instance. Ask the DBA for GRANT CREATE DATABASE in master. The application still deploys.
Schema or metadata failed
Open the log named in the summary. Finish the step in the Schema or Metadata Management workbench, or fix the cause and redeploy. The script has no database-only option, so a redeploy also redeploys the same application build, which is harmless.
"A schema pre/post-deployment step is running … lifecycle procedures cannot be replaced now"
Another deploy or workbench run is mid-lifecycle on that database. Wait for it to finish, then try again.
SQL 2801 "definition of object … has changed since it was compiled"

Before f3bea4de, opening a workbench during a deploy could re-create the lifecycle procedures while they ran. That happened on the QA database on 13 Oct 2026 and left every foreign key to SCore.DataObjects disabled. To check a database, count the keys that are still disabled. The result should be 0:

Read-only check
SELECT COUNT(*) FROM sys.foreign_keys
WHERE referenced_object_id = OBJECT_ID(N'SCore.DataObjects')
  AND (is_disabled = 1 OR is_not_trusted = 1);

If it isn't 0, re-run EXEC SCore.PostDeploymentScript @ThrowOnIssues = 1; on that database as your _adm account, while nobody is using a workbench.

"PowerShell is in NonInteractive mode" at the credential prompt
Run the script from an interactive PowerShell opened as your _adm account, or pass -Credential.
"Deploying from '…', not a release/* branch"
A warning only. Prefer release/*, because any schema sync commit lands on the branch you deploy from.

Safety rules the script enforces

  • QA and UAT only. LIVE is not configured, and LIVE-looking databases are refused.
  • Builds only from committed source. Each file is hash-checked after transfer and again after the switch.
  • The live files are backed up before every switch, and failures roll back automatically.
  • Server-owned config and logs are never touched.
  • The database is migrated only after a verified backup, and schema is applied only through the controlled runner from committed files.
  • No credentials are kept in the script; connections use Windows authentication.

Contract tests in tests/CymBuild.Architecture.Tests (ServerDeploymentScriptSourceContractTests, MigrationBootstrapSourceContractTests) fail the build if any of these rules is removed. Offline tests: pwsh -File tools/Deployment/Tests/Invoke-PublishCymBuildServerTests.ps1.

Known limits

  • DEV contains unreleased work from every branch. All of it reaches QA, and then UAT.
  • A source that's behind can regress the target. If the source holds an older definition than the target, the older one is applied and committed. Check any schema sync commit before pushing it.
  • An accepted run keeps its original selection when it's refreshed.
  • More than 5,000 differing metadata rows fails the metadata step.
  • Metadata identity-map review is not performed unattended.
  • QA to UAT crosses SQL instances. The two-connection metadata path has had gaps before, so read metadata.log after the first UAT run.
  • There's no API health endpoint. The check only proves that Kestrel answers on the port.
