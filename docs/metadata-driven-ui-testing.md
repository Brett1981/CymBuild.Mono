# Testing CymBuild's metadata-driven UI

## The testing problem

A conventional PWA test plan assumes each page owns its controls and behaviour.
CymBuild's `V2FormRenderer`, `V2FieldEditor`,
`FilteredDynamicGridViewV2`, and related components instead interpret metadata.
A single code change may affect many screens, while a metadata-only change may
affect a screen without changing Razor or C#.

The solution is contract testing across renderer capability, metadata instance,
binding, and journey—not screenshot or page-count testing alone.

## 1. Renderer capability contracts

Create compact synthetic metadata fixtures for each supported capability and
important combination. Confirm the exact model types and builders from the
current repository before adding fixtures.

Candidate capability groups:

- field types and value conversion;
- required, range, format, cross-field, and server validation display;
- default, null, read-only, enabled, and hidden behaviour;
- conditional visibility/enabling;
- user/role/organisational-unit permissions;
- labels, help, grouping, ordering, and layout semantics;
- lookup/dropdown loading, selection, no-results, and error handling;
- actions, save/cancel, dirty state, duplicate prevention, and busy state;
- grid columns, formatting, filtering, sorting, paging, empty/error states;
- accessibility name, role, focus, keyboard interaction, and error association;
- cancellation and stale/asynchronous response protection.

Assert rendered semantics and callbacks/state. Use focused markup assertions
only when markup itself is a compatibility/accessibility contract.

## 2. Metadata manifest contracts

Every source-controlled metadata definition should be validated without opening
a browser. The validator/compiler should check:

- schema/version compatibility;
- required stable Guids and controlled natural keys;
- uniqueness and duplicate prevention;
- dependency existence and acyclic ordering;
- **Grid → View → Columns** ordering;
- referenced entity/property/query/column/action availability;
- renderer support for the declared field/column/action type;
- validation rule shape and mutually inconsistent settings;
- permission/security references;
- no environment-specific numeric IDs where stable identity is required;
- no orphan, target-only, or missing dependency after apply;
- deterministic/idempotent serialisation and apply order.

This is the broadest coverage layer: it should run for every manifest in every
pull request that can affect metadata interpretation.

## 3. Binding contracts

Rendering a button is not proof that it performs the correct operation. For each
action binding, statically or deterministically resolve:

```text
metadata action → renderer event → FormHelper method → gRPC contract
```

Where persistence is involved, integration coverage continues through the API
and EF/SQL boundary. The binding catalog should flag an action that bypasses
FormHelper, points to a missing method/contract, or has no validation/error test.

## 4. Critical E2E journeys

Choose journeys by business and production risk rather than trying to run every
metadata permutation in a browser. Typical categories, to be confirmed from the
current product scope, are:

- authenticate and open an authorised metadata-driven view;
- search/filter/open a record from a dynamic grid;
- create or edit a managed entity and verify successful reload;
- exercise one valid and one invalid workflow transition;
- verify permission-denied/read-only behaviour;
- confirm a critical integration-triggering action creates the expected local
  result without directly calling an external dependency.

LIVE runs are restricted to approved, non-mutating health, authentication,
render, navigation, and read-only query checks. Create/edit/transition journeys
run in controlled DEV/QA/UAT data arrangements only.

## Stable selectors

Browser tests need stable semantic identifiers generated by the generic
renderer. A suitable design is to expose test attributes derived from existing
stable metadata identity, for example:

```text
data-cyb-screen
data-cyb-field
data-cyb-action
data-cyb-grid
data-cyb-column
```

These names are a proposal, not an instruction to patch unknown components.
Inspect the existing renderer and accessibility attributes first. Reuse an
established convention if one exists. Values should use controlled manifest
Guids/keys, never numeric database IDs or translated captions.

Preferred locator order:

1. accessible role and stable accessible name when wording is a product
   contract;
2. established stable metadata-derived identifier;
3. a purpose-built test attribute at the shared renderer layer.

Avoid DOM index, implementation-only CSS classes, text that metadata/localisation
can change freely, and fixed sleeps.

## Representative combinations

Do not use a full Cartesian product of every metadata option. Use pairwise or
risk-based combinations plus explicit tests for known interactions. Always add
a regression fixture for an actual defect and keep its intent/source traceable.

## Metadata promotion verification

Metadata deployment tests must cover:

- same Guid/same content is a no-op;
- same Guid/changed content is a controlled update;
- numeric ID differences do not change identity;
- dependency mapping and ordered apply;
- duplicate prevention;
- rerun after complete success;
- partial failure and supported retry;
- ignored/overridden records;
- preview and apply use the same approved definition/hash;
- missing/orphan/target-only items and post-apply drift;
- concurrent or repeated invocation where supported.

Verification compares the deployed result to the approved source definition. It
must not silently use target contents as the new source of truth.
